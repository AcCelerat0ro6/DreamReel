# 推荐会话队列性能对比与简历技术亮点

测试日期为 2026-11-06，时区为 Asia/Hong_Kong。

## 结论

在本机、模拟数据和指定负载下，新方案显著降低了会话内翻页成本。缓存翻页 P95 的三轮中位数从 **74.80 ms 降至 4.64 ms，降低 93.8%**，平均每请求 MySQL 查询从 **4.011 次降至 2.011 次，减少 49.9%**。

包含首屏的连续刷流也获得了更高的观测吞吐量，20 VU、每次迭代刷 8 页时，旧版为 **171.94 请求/秒**，新版为 **669.72 请求/秒，达到原来的 3.90 倍**。这是该闭环负载下的观测值，容量上限尚未测定。

建池成本同时增加。50 RPS 首屏场景中，P95 从 **66.45 ms 增至 119.98 ms，增加 80.5%**。连续刷流场景的单请求 P95 也从 **140.30 ms 增至 168.71 ms，增加 20.2%**。首屏与补池集中处理较多候选，会影响尾延迟。

新方案长会话中，普通缓存页 P95 为 **8.61 ms**，首屏 P95 为 **162.28 ms**，补池页 P95 为 **166.14 ms**。该场景每次迭代请求 25 页，跨过首批 200 条候选的边界。三轮完成 **1,450 次完整刷流迭代**，每次返回 250 条视频，未记录到会话内重复。

## 为什么查询减少

旧版每次翻页重新执行候选池召回、加载视频向量、读取用户画像并精排，然后组装卡片和互动状态。新版将精排结果保存到会话队列，普通翻页读取既定序列，只保留批量可见性检查和用户互动状态读取等必要查询。

查询计数在 `database/sql` 驱动层采集，预编译语句的实际执行计数一次。返回 `driver.ErrSkip` 的回退调用排除重复计数。预热完成后重置计数，正式请求结束后冻结计数，所以表中的 SQL/请求覆盖了真实接口链路。

原先在每次请求支付的召回、向量加载和排序成本，现在主要集中在建池与补池。初次召回从旧版每页对应的 80 个候选增加到 200 个，首屏还要写入 Redis 队列、元信息和去重集合。这个设计适合持续刷流，需要结合首屏和会话存储成本评估。

## 可直接用于简历

推荐采用下面两条，根据简历篇幅选择保留。

- **推荐分页优化**。设计并实现基于 Redis List 的 Session 推荐队列，结合已入队去重、Lua 版本校验原子补池、游标绑定及视频可见性过滤，支持跨批次稳定分页与并发补池。
- **性能验证**。搭建可复现 k6 A/B 压测，在 1 万视频、64 个用户画像、128 维向量的模拟数据及目标 100 RPS 下，三轮本机测试将会话内翻页 P95 从 74.80 ms 降至 4.64 ms（降低 93.8%），MySQL 查询由约 4 次/请求降至约 2 次/请求。

面试讲解时可以补充以下内容。

- 选择缓存精排结果，让会话内序列稳定，并保留视频可见性和用户互动状态的实时读取。
- 说明建池、普通翻页和补池的不同成本。首屏 P95 增加约 80.5%，连续 8 页的单请求均值降低约 74.5%，体现了批量计算的摊销。
- 20 VU 连续刷流观测到约 3.90 倍吞吐量，该数值对应本机给定负载条件。简历中的核心量化指标优先采用相同目标到达率下的会话内翻页延迟和每请求 SQL 次数。
