# DreamReel 性能测试报告

2026 年 11 月 13 日，实验室服务器 `target-wsl`。本报告覆盖 16 组场景、128 轮单侧测量，从推荐、卡片组装、连续刷流一直测到互动落库。表中 A 表示对照，B 表示项目当前使用的路径或缓存命中状态。推荐分页直接构建历史提交作对照，其余各项的开关与构造方式见场景说明。

## 结果汇总

**推荐会话队列的收益集中在连续使用。** 在 1 万视频、4 个并发客户端下，第二页 P95 从 **26.55 ms 降至 1.58 ms（降低 94.1%）**。即使计入首屏建池，取完连续 8 页的 P95 也从 **205.09 ms 降至 43.14 ms（降低 79.0%）**。只看首屏则多花了 7.35 ms。

|---|---|---:|---:|---:|---:|

| 时间线首页 | SQL → 已预热的 Feed 缓存 | 2.58 ms | 2.68 ms | ↑ 3.7% | 4,365 → 4,795 请求/s |

| 客户端连续追加 1 万条 | 全量保留 → 有界缓冲 | P50 189.073 → 5.650 ms | 列表末态 10,000 → 200 条，保留当前项与最近回看项 |

深分页在两侧都只执行一次 SQL。实际执行计划解释了差距。OFFSET 路径选择扫描整张视频表并排序，索引游标路径由 `idx_video_timeline` 定位到边界后读出所需的 11 行。执行计划中的时间另行采集，表中延迟取自重复的仓储测量。[MySQL EXPLAIN ANALYZE 原文](../benchmarks/lab/results/20261113/plans.txt)

AIGC 模型榜单体现了不同的取舍。SQL 聚合把数据库返回的行数减少了 99.89%，在同机 Unix socket、1 万部作品和 16 个模型的条件下，P95 却从 12.47 ms 升至 17.25 ms。这个结果能支持“减少行传输”的描述，无法支持“榜单响应加速”的描述。

### 异步互动把等待移到了哪里

| 指标（每轮 192 次首次操作） | 收藏·同步 | 收藏·异步 | 点赞·同步 | 点赞·异步 |
|---|---:|---:|---:|---:|
| HTTP 全部返回后至确认落库 | 12.4 ms | 1,676.3 ms | 12.6 ms | 1,486.9 ms |
| 含最终持久化确认的吞吐（操作/s） | 118.17 | 111.66 | 79.83 | 104.50 |

异步组四轮共核对了 **768 条收藏消息和 768 条点赞消息**，最终行为数、视频计数都相符，点赞通知也通过检查。收藏的响应吞吐达到同步路径的 37.9 倍；含全部持久化的吞吐由 118.17 变为 111.66 操作/s。点赞的异步组四轮 P95 在 26.58–47.08 ms 之间，其通知写入仍在请求路径上。

## 测试环境与统计方法

| 项目 | 本次设定 |
|---|---|
| 主机 | 实验室 WSL2，Intel Core i7-12700，客体可见 20 个逻辑 CPU，约 15.5 GiB 内存。压测客户端与服务端同机 |
| 运行时 | Go 1.26.8 linux/amd64，Go 进程各设 `GOMAXPROCS=4`。每个 API 实例的 MySQL 连接池最多 32 条、空闲 16 条 |
| 服务 | 独立 MySQL 8.4.13，InnoDB 缓冲池 256 MiB，事务提交与 binlog 同步参数均为 1，数据文件在 ext4；独立 Redis 8.0.5；实验机 RabbitMQ 4.0.5 使用随机专用 vhost |
| 数据 | 10,000 个已发布视频、20,000 个合成账号、64 位发视频的作者、10,015 条关注关系、10,000 个 128 维向量。每 10 条视频共享一个发布时间，给游标排序制造同秒边界 |
| 分布 | 固定随机种子 20261113 生成 64 个稠密单位向量，按 ID 分配给视频。互动计数由 ID 的固定模数生成。主要读测试使用同一位有 200 条完播记录的用户，他关注 1 位万粉作者、15 位普通作者 |
| 源码 | 推荐 A 使用 `1cfc6fd`，B 使用当前工作区，HEAD 为 `6b65c88` 并含未提交修改。打包时同时固化两版生产源码、依赖清单及测试代码的 SHA-256 |

每个场景做四轮配对，顺序按 A/B、B/A 交替执行。表中 P95 先对该轮样本排序，取排名向上取整的第 95 百分位，再对四轮取中位数。变化率按未舍入的 A、B 计算。同一张表中每行的计量单位见场景名，例如整波、整段会话、一次发布或单次 HTTP 请求。逐轮均值、P50、P95、P99 和样本量均保存在 CSV；每轮只有 5 或 12 个样本的场景，P95 等于该轮观测最大值，正文优先讨论其中位数或工作量。

常规组件场景每侧先执行一次不计时调用，计时包含实际 Go 代码、存储访问及结果校验。冷启动并发场景单独以屏障同时放行。组件 SQL 次数来自 GORM 的已执行语句回调；单页回源次数另在仓储入口计数。HTTP 组编译两个版本的完整生产路由，使用签名 JWT，经 HTTP/1.1 和私有 Unix socket 发请求，客户端计时包含完整读取、JSON 解码和断言。每轮新建闭环线程池，各线程复用连接，为计时前的参考调用使用另一连接。吞吐量用完成操作数除以包含客户端调度的整轮墙钟时间。CPU 调度、数据库热页及共享消息代理会带来波动；这些短轮次用于比较指定负载，尚未测定持续容量、公网延迟或真实用户体验。

## 每组对照怎么做

### 推荐分页 · 首屏、第二页与连续 8 页

通过 `GET /api/feed-items?scene=recommend&limit=10` 分别请求改造前后的 API。两版读取同一不变的视频和画像数据，各用自己的 Redis 逻辑库，均启用卡片缓存。旧版每页召回最多 80 个候选，重排后按分数游标过滤；新版首屏建 200 条候选会话队列，后续从队列读并批量校验当前可见性。推荐算法和返回顺序允许随版本变化，固定页核对各自版本的预热结果。

- **首屏**每次发送空游标，4 个客户端、每侧每轮 100 次，包含建池费用。
- **会话内第二页**取一次真实首屏游标，预热第二页后，4 个客户端固定重放该游标，每侧每轮 100 次。该数字刻画缓存命中路径。
- **连续 8 页**每个会话从空游标开始，逐页使用上次响应的游标，每页 10 条。每侧每轮 30 个会话，4 个并发。逐页检查 HTTP 200、页长和页内唯一性，并统计一个会话中重复的视频。时延单位是用户取完 80 条的整段耗时，覆盖首屏建池。旧版候选池可在第八页用尽；测试只在继续请求下一页时要求有效续页。该场景没有跨过新版补池边界。

### 时间线 · 深分页、卡片组装、热点冷启动与整页缓存

1. **深分页**在两侧保留生产联合索引和相同字段投影。A 按 `published_at DESC, id DESC` 跳过 9,000 行取 11 行；B 调用生产 `ListTimelinePage`，从上一页末项的时间及 ID 续取同样 11 行。锚点准备在计时外，因为正常连续翻页已经持有上一页游标。每侧每轮 240 次，逐次检查记录、顺序、作者和时间。这个比较适用于连续翻页；随机跳到指定页仍要先定位锚点。
2. **卡片组装**固定 20 个视频，包含该用户已点赞与未点赞的内容。A 对每个视频单独调用卡片、统计、用户状态三个生产仓储方法；B 将同一批 ID 各传入一次。每侧每轮 120 页，逐条核对完整数据。对照是构造的逐条读取方式；测量范围到仓储数据就绪。
3. **并发回源**先预热卡片和计数，再仅删除时间线首页骨架键。32 个 goroutine 同时访问同一页，每侧每轮 40 波。A 使用各自的策略实例，无法共享 singleflight group；B 共享部署进程内的策略。两侧均执行 Redis 检查、数据库回源、缓存写回和卡片组装，并校验整页相等。A 中晚到的请求仍可能命中刚写回的缓存。结果中的“回源/波”只计页面骨架查询，毫秒数计从放行到 32 个请求全部完成。
4. **时间线 HTTP 首页**使用已登录用户和生产路由，A 关闭 Feed 缓存，B 预热页、卡片及统计缓存，均保留用户互动状态查询。8 个客户端，每侧每轮 480 次，同一页的响应卡片与 SQL 参考页逐项一致。这一组检验组件级节省能否传导至完整接口。

### 滚动热榜和用户画像

- **热榜分钟桶**把 10,000 个视频的分数分布到固定截止时间前的 60 个分钟桶，生产 `AddHotScore` 写入。A 在每次计时前删除派生窗口，触发 `ZUNIONSTORE`、清理非正分值、设置 TTL 并读取 Top 11；B 复用同一截止时间的窗口。每侧每轮 120 次，逐个校验视频 ID 和分数。同一工作负载体现窗口有效期内的摊销；窗口过期时仍需付 A 的代价。数据库累计热度榜的时间语义不同。
- **画像读取**使用同一用户、同一批 200 次完播与同一批向量。A 删除该用户画像，让生产仓储走在线聚合；B 在计时前调用生产 `RefreshUserInterestProfile` 生成快照后读取。每侧每轮 160 次，校验所有 128 个分量，容差为 1e-12。B 把计算移到画像刷新阶段，本项只计读路径。

### 关注流 · 同一位作者的发布成本和读者的取流成本

- **万粉扇出**在 MySQL 构造 10,000 条真实的目标关注关系。两侧使用生产 FanoutWorker、相同的时间戳和每次不同的视频 ID。A 的测试适配器仍执行粉丝计数查询，再强制走全量推送分支；每 500 位粉丝批量写入 Redis 收件箱。B 按真实的 10,000 人阈值写一次作者发件箱。每侧每轮 12 次发布，排除两侧共同的视频预热及 MQ 投递；核对抽样粉丝收件箱和作者发件箱中的唯一发布数。A 承担写放大；B 将大作者作品的合并工作交给读取端。
- **关注流 HTTP 首页**同一用户关注 16 位有作品的作者，提前准备普通作者收件箱和大作者发件箱。A 走关系 JOIN、时间排序和 SQL 卡片组装；B 查需拉取的作者，用 Redis pipeline 读取收件箱和发件箱后合并去重，再用预热的卡片缓存组装。每侧每轮 480 次、并发 8，逐字段比较两侧的 10 个结果。这是整条缓存路径的综合效果，无法把全部差值归因于推拉合并。

### AIGC 模型热度榜

模拟 1 万部作品分属 16 个模型。对照组从 MySQL 一次读回所有符合发布条件的作品及其计数，在 Go 中按模型名聚合；项目实现通过生产仓储 `ListModelRankings` 在 MySQL 完成 JOIN、GROUP BY、加权求和、排序和 LIMIT。两侧均按点赞 × 3、评论 × 5、收藏 × 4 计算热度，并按作品数和模型名打破平局，取 11 条供首页展示 10 条并判断是否还有下一页。每侧每轮 100 次，逐字段比较完整前 11 名。夹具使用 ASCII 模型名；此项衡量的是应用与数据库之间传多少行、在哪里聚合。[榜单基准源码](../apps/api/test/performance/rankings_test.go)

### 异步互动 · 请求返回、消费、持久化

分别测收藏和点赞。每侧每轮 192 位不同用户首次操作同一热门视频，并发 12；轮间更换视频。A、B 均启用 Redis 热度记录。A 调用同步事务写行为和计数，B 读取初始计数，通过 Redis WATCH、事务和分片计数更新状态，投递 RabbitMQ，由单个消费者调用生产 ActionWorker 写回 MySQL。点赞比收藏多出作者通知链路。预热用另一个视频，预签 JWT；每次检查响应、目标视频、互动类型及生效状态。

当一轮 HTTP 请求全部返回后，独立查询验证 MySQL 最终计数较初始值增加 192，且对应用户范围内有 192 条有效行为。异步组还校验成功处理的消息数恰好增加 192，以排除发布失败后回退到同步写入。点赞组核对 192 条唯一事件对应的通知。**确认尾时长**从整轮 HTTP 结束算至上述数据库条件首次成立，包含客户端查询启动与轮询开销；**落库吞吐**用 192 除以整轮请求及确认耗时。两项都是单批次观测，没有把入队速度当作数据库写入速度。

### 客户端长刷与部署静态资源

- **推荐流缓冲**通过 Node 直接调用前端共用的 `appendFeedItems` 和 `feedTrimCount`。模拟连续前进 1,000 页、每页 10 条唯一记录。A 累积完整列表，B 按线上策略裁剪；核对当前条目与向前回看 20 位的数据。每侧每轮重复 5 个完整长会话。记录保留条目数和纯数组逻辑耗时；点赞字典清理、React 渲染、DOM、视频解码、浏览器内存与首帧时间均在计时范围之外。
- **静态 JS 缓存验证**直接读取实验机已部署 Nginx 首页，解析 Vite 入口 JS，以同一 HTTP 连接对同一文件交替发普通 GET 或携带该文件 ETag 的条件 GET。每侧每轮 20 次。核对 200 的完整正文与 304 的空正文，记录 Cache-Control、资源 SHA-256、正文长度和耗时。这里计的是一次重新验证；在浏览器本地新鲜期内，实际还可能完全省掉请求。本实验没有测公网传输或浏览器加载指标。

## 可直接写进简历

> 为 DreamReel 短视频社区实现基于 Redis 会话队列的推荐分页，将候选召回与排序按会话复用，并通过批量查询组装 Feed 卡片。在实验室 1 万视频、4 并发客户端的四轮 A/B 压测中，将推荐会话内翻页 P95 从 26.55 ms 降至 1.58 ms（降低 94.1%），含首屏的连续 8 页 P95 从 205.09 ms 降至 43.14 ms；在 20 条/页的独立组装测试中，相比逐条读取，将卡片、计数和互动状态查询从 60 次 SQL 降至 3 次。
